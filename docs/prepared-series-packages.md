# Prepared series packages, version 1

Open Series → Import prepared package. Select a manifest and its referenced files (or a folder). Plain uploaded files are used; the server never reads your filesystem. ZIP/TAR/GZ/7z archives, absolute paths, traversal, backslashes, NUL, colon paths, duplicate uploaded paths and missing references are rejected. Folder upload strips its selected top-level folder when matching manifest-relative paths. Only referenced Markdown and still PNG/JPEG/WebP heroes are sent.

The complete example is [examples/prepared-series-v1.json](examples/prepared-series-v1.json). Required top-level fields: schemaVersion (1), packageKey (stable, at most 160 characters), brandId (an authorized workspace brand), title and entries. Each entry has a unique stable key, one article and zero to ten companions. Each companion has its own key, social channelId and title. Every item requires contentFile, scheduledDate (real YYYY-MM-DD), scheduledTime (HH:MM) and an IANA timezone (or UTC). Invalid/nonexistent/ambiguous DST local times require an explicit corrected schedule; the importer never shifts a date to now. Past dates remain visible in preview and require later delivery review.

Articles additionally require heroFile, coverImageAlt, publicationIntent (draft or published), excerpt, author, category, nonempty tags and a URL-safe slug. Optional crop is centre (default), north or south. Optional existingPostId requests attachment of the exact authorized matching item. LinkedIn companions may have firstComment; it is preserved exactly and will be capability-checked before any later dispatch. These fields are editorial input, not approval or publish authority.

Bounds: at most 100 entries, ten companions per entry, 250 KB manifest, 50 KB UTF-8 Markdown per item, 3 MB source image, 50 MB/500 uploaded files per package, with at most 5 MB of Markdown total. Durable review history for one package key is bounded to 6 MB; split large/repeatedly revised packages into new explicitly reviewed keys. Each entry is reviewed/committed separately, keeping Node arguments below 5 MiB and durable review rows below 1 MiB. Large packages can use separate stable package keys. No archive extraction is provided.

Dry-run validates the entire manifest and referenced files before entry processing, then stores durable per-entry review records. It creates no posts, series links, assets, approvals, PRs, provider mutations or AI requests. Preview shows create/attach/skip/conflict, exact source text and metadata, SHA-256 source and prepared hero receipts, and local/UTC schedules. No title/body normalization, Markdown frontmatter removal, prose rewriting, number alteration or link inference is performed. The hero preview prepares a separate fixed-dimension derivative in memory; commit stores the original and derivative separately.

Read the whole plan and explicitly click Commit reviewed entries as unapproved drafts. Each entry creates its posts through the canonical creation helper, including publishing intent, provider state and audit history; all new posts remain unapproved. The series groups those same post IDs. existingPostId attachment requires matching copy/metadata/schedule and, for an article, matching original hero bytes and prepared crop/receipt. Existing approval, delivery state and publication history are retained without edits.

Stable package/entry keys and canonical source SHA-256 fingerprints recover completed entries across interruption/reload. Re-upload identical input, run dry-run and commit: completed entries are skip/no-op, and incomplete entries continue. Shared identical hero source/crop receipts reuse one stored asset pair. Changed input for a committed key conflicts; it never updates old copy, even when an old post remains unapproved. Review explicitly and use a new key for a new editorial item. Package title/brand conflicts require a new package key.

An unresolved asset claim is held rather than retried blindly. If execution terminates between storage and receipt persistence, retain the claim and inspect/reconcile the receipt before another upload; no automatic duplicate asset creation occurs. Ordinary caught storage failures clean up new orphan bytes, with the retained claim still visible for investigation. This differs from a completed per-entry receipt, which always resumes automatically and idempotently. Commit-time ownership/content checks run again before any post write; one entry's transaction is atomic.

Imports do not bind publication dependencies automatically. Use the canonical companion composer to review its parent article, final URL and placement before batch approval/queue release.
