Storage protection is additive in data but changes access rules: newly uploaded bytes carry indexed owner/brand evidence; visual refs/versions/exports are protected; historical attachments require explicit saved-post context. Bare orphan storage IDs are denied. Compatibility for historical attachments is covered by the coordinator's tests/review, not by production data readback in this report. A release must retain these guards and the same-snapshot publication manifest gate. Native `sharp` is declared in `convex.json` external packages; actual production Node packaging and export execution still require post-deployment verification with authorized nonpaid bytes.

Convex explicitly treats new tables and optional fields as safe evolution patterns, while existing data must match listed validators. [Production changes](https://docs.convex.dev/production/overview) and [schema validation](https://docs.convex.dev/database/schemas) are the relevant primary references. Removing a table from a schema does **not** delete its stored documents: tables outside the schema can remain and are unvalidated. That means a blind return to the baseline schema can discard validation/index/function coverage while leaving visual lineage and reservations stranded. It is not a data-preserving rollback strategy by itself.
